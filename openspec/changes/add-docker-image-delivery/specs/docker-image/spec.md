# Spec Delta: docker-image

Контракт поставки `tldr` как контейнерного образа: как образ запускается, что он гарантирует
и что в нём не поддерживается.

## Purpose

Возможность запускать все команды анализа `tldr` в любом проекте без установки инструмента:
образ из реестра контейнеров получает проект, смонтированный только для чтения, и выдаёт результат
так же, как установленный бинарь.

## ADDED Requirements

### Requirement: Точка входа и аргументы
Образ SHALL запускать `tldr` как точку входа и передавать ему без изменений все аргументы,
указанные после имени образа. Рабочий каталог контейнера SHALL быть `/project`. Запуск без аргументов
SHALL выводить справку `tldr`.

#### Scenario: Подкоманда с относительным путём
- **WHEN** пользователь выполняет `docker run --rm -v "$PWD:/project:ro" <образ> structure .`
- **THEN** выполняется `tldr structure .` над каталогом `/project` и результат выводится в stdout

#### Scenario: Запуск без аргументов
- **WHEN** пользователь выполняет `docker run --rm <образ>`
- **THEN** выводится справка `tldr` и контейнер завершается с кодом `0`

### Requirement: Код возврата
Код возврата контейнера SHALL совпадать с кодом возврата `tldr`.

#### Scenario: Неизвестная подкоманда
- **WHEN** пользователь передаёт подкоманду, которой нет в `tldr`
- **THEN** контейнер завершается тем же ненулевым кодом, что и `tldr` вне контейнера

### Requirement: Проект только для чтения
Команды анализа, не изменяющие проект по своему назначению, SHALL работать при монтировании
проекта в `/project` в режиме только для чтения и SHALL NOT требовать записи в `/project`.

#### Scenario: Анализ проекта под :ro
- **WHEN** проект смонтирован `-v /путь:/project:ro` и выполняется `tree`, `structure` или `calls`
- **THEN** команда завершается с кодом `0` и выдаёт валидный JSON

### Requirement: Каналы вывода
Основным каналом результата SHALL быть stdout. Каталог `/out` SHALL быть необязательным: команды,
не записывающие файлов, SHALL работать без его монтирования, а файл, путь которого пользователь
указал внутри `/out`, SHALL появляться в смонтированном каталоге хоста.

#### Scenario: Результат через stdout
- **WHEN** пользователь выполняет команду анализа без монтирования `/out` и перенаправляет stdout в файл
- **THEN** файл на хосте содержит полный результат команды

#### Scenario: Запись файла в /out
- **WHEN** смонтирован `-v "$PWD/out:/out"` и выполняется `fix apply -s <файл> ... -o /out/patched.py`
- **THEN** на хосте появляется `out/patched.py`

### Requirement: Произвольный пользователь
Образ SHALL работать под любым идентификатором пользователя (User Identifier, UID) и группы, переданным через `-u`, и SHALL запускаться
под непривилегированным пользователем, если `-u` не указан.

#### Scenario: Запуск под UID хоста
- **WHEN** образ запускается с `-u "$(id -u):$(id -g)"` при UID, отсутствующем в образе
- **THEN** команды анализа выполняются без ошибок доступа

#### Scenario: Запуск без -u
- **WHEN** образ запускается без `-u`
- **THEN** процесс `tldr` выполняется не от `root`

### Requirement: Команды на основе истории git
Команды, читающие историю git, SHALL работать с репозиторием, смонтированным только для чтения
и принадлежащим другому UID, чем процесс контейнера.

#### Scenario: churn под чужим UID
- **WHEN** репозиторий с каталогом `.git` смонтирован `:ro`, контейнер запущен под UID, отличным от владельца, и выполняется `churn`
- **THEN** команда завершается с кодом `0`, без отказа git из-за владельца каталога

### Requirement: MCP-сервер в образе
Образ SHALL содержать сервер протокола контекста модели (Model Context Protocol, MCP) `tldr-mcp`, работающий через stdin/stdout при запуске
с `-i` и `--entrypoint tldr-mcp`.

#### Scenario: Инициализация MCP
- **WHEN** выполняется `docker run -i --rm -v "$PWD:/project:ro" --entrypoint tldr-mcp <образ>` и в stdin передаётся запрос `initialize`
- **THEN** сервер отвечает в stdout ответом на `initialize`

### Requirement: Теги образа
Выпуск с тегом git `vX.Y.Z` SHALL публиковать образ с тегами `X.Y.Z`, `X.Y` и `latest`.
Пре-релиз `vX.Y.Z-<суффикс>` SHALL публиковать только тег `X.Y.Z-<суффикс>`.
Push в рабочую ветку `TLDR-*` SHALL публиковать только тег `dev-<короткий sha коммита>`.

#### Scenario: Выпуск
- **WHEN** в репозиторий отправлен тег `v0.5.0`
- **THEN** в реестре появляются теги `0.5.0`, `0.5`, `latest`, указывающие на один образ

#### Scenario: Пре-релиз
- **WHEN** в репозиторий отправлен тег `v0.5.0-rc.1`
- **THEN** публикуется только тег `0.5.0-rc.1`, а `0.5` и `latest` не меняются

#### Scenario: Проверочный образ рабочей ветки
- **WHEN** в ветку `TLDR-001-docker-image` отправлен коммит `abc1234`
- **THEN** публикуется только тег `dev-abc1234`, а теги выпусков и `latest` не меняются

### Requirement: Согласованность версий
Версия, которую печатает `tldr --version` в образе, SHALL совпадать с тегом образа и версией crate.
Если тег выпуска не совпадает с версией workspace, образ SHALL NOT публиковаться.

#### Scenario: Тег расходится с версией
- **WHEN** отправлен тег `v0.5.0`, а версия workspace — `0.4.0`
- **THEN** публикация не выполняется и workflow завершается ошибкой

### Requirement: Архитектуры
Каждый публикуемый тег SHALL указывать на образ для `linux/amd64` и `linux/arm64`.

#### Scenario: Запуск на arm64
- **WHEN** `docker pull` выполняется на хосте `linux/arm64`
- **THEN** загружается нативный arm64-образ без эмуляции

### Requirement: Метаданные образа
Образ SHALL нести метки формата Open Container Initiative (OCI) `org.opencontainers.image.source`, `version`, `revision` и `licenses`;
`source` SHALL указывать на `https://github.com/united-software-platform/tldr-code`, `licenses` — на `AGPL-3.0`.

#### Scenario: Проверка меток
- **WHEN** пользователь выполняет `docker inspect` для опубликованного образа
- **THEN** метки содержат репозиторий-источник, версию выпуска, коммит сборки и лицензию

### Requirement: Проверка перед публикацией
Образ SHALL NOT публиковаться, если не прошёл дымовую проверку: запуск под произвольным UID на проекте,
смонтированном только для чтения, с проверкой команд анализа, команды на основе git и MCP-сервера.
На запросе слияния (Pull Request, PR) проверка SHALL выполняться без публикации.

#### Scenario: Проверка не прошла
- **WHEN** дымовая проверка завершается ошибкой при сборке по тегу выпуска
- **THEN** ни один тег образа не публикуется

#### Scenario: Проверка на PR
- **WHEN** открыт PR, затрагивающий репозиторий
- **THEN** образ собирается и проверяется, но в реестр не публикуется

### Requirement: Документированные ограничения
Документация образа SHALL перечислять, что в образе не работает: семантический поиск (`embed`,
`semantic`, `similar`), daemon, команды с записью в проект под `:ro` (`warm`, `cache clear`, `fix apply -i`),
сравнение с базовой версией в `bugbot`, внешние линтеры.

#### Scenario: Команда семантического поиска
- **WHEN** пользователь вызывает `semantic` в образе
- **THEN** `tldr` сообщает о неизвестной подкоманде и завершается с ненулевым кодом, как описано в документации

#### Scenario: Запись в проект под :ro
- **WHEN** пользователь вызывает `warm` при проекте, смонтированном `:ro`
- **THEN** команда завершается с ненулевым кодом и сообщением об ошибке записи, а проект на хосте не изменяется
